/implement

Builds a ticket from its approved plan in a fresh session: tests first, then code. Two hooks come with the skill: a lock that keeps the approved tests and plan unchanged, and a gate that only lets Claude finish when every AC test and check passes.

What makes it good

  • Hooks that come with the skillThe hooks are in the skill's frontmatter. They turn on when /implement starts, so they don't get in the way of other work.
  • Tests from a separate agentThe test-writer subagent writes the tests from acs.md only, without the plan's code steps. The tests and the code come from two agents, so they can't share one misreading.
  • Tests must fail firstA test that passes before the code exists tests nothing. The human approves the failing tests before the build.
  • Approved tests are lockedDuring the build, edits to the test files, acs.md, sequence.md and plan.md are blocked, through edit tools and shell commands. Fix the code, not the test.
  • Can only finish when greenThe Stop hook runs every test command and check from plan.md. If one fails, Claude keeps working.
  • No endless loopAfter 5 failed tries the gate lets Claude stop and tells the human. The lock stays on.
  • Logic check before finishingThe review-logic subagent reads the code against each AC before the gate runs.
  • Only the planned filesA file outside the plan means the plan was wrong, so Claude stops and asks.

# Implement: approved plan → working code

You build exactly what `plans/<TICKET>/plan.md` says. A separate subagent writes the tests first, from the ACs only. Two hooks come with this skill and stay on for the rest of the session:

- **Lock** (before every edit): during the build, the approved test files, `acs.md`, `sequence.md` and `plan.md` can't be changed.
- **AC gate** (when you try to finish): runs every test command and check in the plan. If one fails, you keep working.

Ticket: $ARGUMENTS

## 1. Check the plan

Read `plans/<TICKET>/acs.md`, `sequence.md` and `plan.md`.

Stop if `plan.md` is missing, has no `Status: approved` line, or has no Tests table: "There is no approved plan. Run /plan <TICKET> first."

Write `plans/.implementing`:

```json
{ "ticket": "<TICKET>", "phase": "tests" }
```

## 2. Tests from the intent (phase: tests)

Start the `test-writer` subagent with the ticket id. It writes every test in the Tests table from `acs.md` only, before any code, and runs them. **You don't write or change tests yourself.** The tests and the code come from two different agents, so they can't share one misreading of the plan.

Check what it returns: every test exists, uses the AC's values, and **fails for the right reason** (the behavior is missing, not a typo or a build error). If not, send it back with what is wrong.

Show the user the tests and the failing output, then ask:

> These are the tests for AC1–AC3 and the "must never" rule, written from the ACs only. They fail because the feature doesn't exist yet. Approve them? After this they are locked.

Only on yes, change `plans/.implementing` to `"phase": "build"`. From now on the lock hook blocks every edit to these tests. On no, ask what is wrong and send it back to `test-writer`.

## 3. Build (phase: build)

Follow the steps in `plan.md` in order. After each step:

- run the test commands for that step's AC;
- use the skills the plan names (for example `add-ef-migration`).

Change only the files in the Files table. If you must change another file, stop and ask: the plan was wrong, and a human should decide.

If a test fails, fix the code, not the test. The lock blocks test edits; don't try to get around it. If you believe a test is wrong, stop and explain why to the user.

## 4. Check against the ACs

Before you finish, start the `review-logic` subagent with the ticket. It reads the code against each AC: missing, extra, edge cases. Fix every blocking finding.

## 5. Finish

When you stop, the AC gate runs every command in the Tests table and the Checks list.

- **All pass** → the gate removes `plans/.implementing`, and the hooks stop doing anything.
- **Something fails** → the gate sends you back with the output. Fix it.
- **Fails 5 times in a row** → the gate lets you stop and tells the user. Write what blocks you.

Then report:

```
JIRA-1234 built.
Tests: 5 of 5 pass (AC1, AC2, AC3, must never, E2E)
Checks: 3 of 3 pass
Files: 11 of 11 from the plan, no others
Next: run /review JIRA-1234
```

Nothing is committed. The human reviews and commits.

PreToolUse hook. In the build phase it blocks edits to the approved tests, the intent files and the marker, also through shell commands like sed -i or >. Tested.

.claude/skills/implement/scripts/lock.mjs
#!/usr/bin/env node
// PreToolUse hook: during the build phase of /implement, block edits to the
// approved test files, the intent files and the marker itself. Exit 2 blocks.
import { relative, resolve } from "node:path";
import { readMarker, readPlan, root } from "./plan.mjs";

let raw = "";
for await (const chunk of process.stdin) raw += chunk;
let input = {};
try { input = JSON.parse(raw || "{}"); } catch {}

const marker = readMarker();
if (!marker || marker.phase !== "build") process.exit(0);

const plan = readPlan(marker.ticket);
const locked = new Set([
  "plans/.implementing",
  `plans/${marker.ticket}/acs.md`,
  `plans/${marker.ticket}/sequence.md`,
  `plans/${marker.ticket}/plan.md`,
  ...(plan?.tests ?? []).map((t) => t.file),
]);

const block = (what) => {
  process.stderr.write(
    `Locked by /implement: ${what} was approved before the build started. ` +
      `Fix the code, not the test or the plan. If you think it is wrong, stop and explain why to the user.\n`,
  );
  process.exit(2);
};

// Edit / Write: check the file path.
const target = input.tool_input?.file_path ?? input.tool_input?.notebook_path;
if (typeof target === "string") {
  const rel = relative(root, resolve(root, target)).split("\\").join("/");
  if (locked.has(rel)) block(rel);
}

// Bash: block shell commands that write to a locked file (sed -i, >, tee, mv, cp, rm, git checkout/restore).
const command = input.tool_input?.command;
if (typeof command === "string") {
  const writes = /(sed\s+-i|>>?|\btee\b|\bmv\b|\bcp\b|\brm\b|git\s+(checkout|restore|stash))/;
  for (const f of locked) if (command.includes(f) && writes.test(command)) block(f);
}
process.exit(0);

Stop hook. Runs the tests and checks from plan.md and checks the planned new files exist. All green: removes the marker. Red: exit 2 with the output. 5 tries: lets Claude stop and tells the human. Tested.

.claude/skills/implement/scripts/ac-gate.mjs
#!/usr/bin/env node
// Stop hook: Claude can only finish /implement when every test command and
// check in plan.md passes. Exit 2 sends Claude back to work with the output.
import { execSync } from "node:child_process";
import { existsSync, readFileSync, rmSync, writeFileSync } from "node:fs";
import { join } from "node:path";
import { markerPath, readMarker, readPlan, root } from "./plan.mjs";

const MAX_ATTEMPTS = 5;

const marker = readMarker();
if (!marker || marker.phase !== "build") process.exit(0); // not building: nothing to gate

const plan = readPlan(marker.ticket);
if (!plan) {
  process.stderr.write(`AC gate: plans/${marker.ticket}/plan.md is missing.\n`);
  process.exit(2);
}

const runs = [
  ...plan.tests.map((t) => ({ label: `${t.ac} ${t.name}`, command: t.command })),
  ...plan.checks.map((c) => ({ label: "check", command: c })),
];

const failed = [];
for (const r of runs) {
  try {
    execSync(r.command, { cwd: root, stdio: "pipe", timeout: 300_000 });
  } catch (e) {
    const out = `${e.stdout ?? ""}${e.stderr ?? ""}`.trim().split("\n").slice(-15).join("\n");
    failed.push(`✗ ${r.label}: ${r.command}\n${out}`);
  }
}
const missing = plan.files
  .filter((f) => f.change === "new" && !f.file.includes("*") && !existsSync(join(root, f.file)))
  .map((f) => `✗ planned new file missing: ${f.file}`);

const attemptsFile = join(root, "plans", marker.ticket, ".gate-attempts");

if (failed.length === 0 && missing.length === 0) {
  rmSync(markerPath, { force: true });
  rmSync(attemptsFile, { force: true });
  process.exit(0); // all green: Claude may finish, hooks go quiet
}

const attempts = (existsSync(attemptsFile) ? Number(readFileSync(attemptsFile, "utf8")) || 0 : 0) + 1;
writeFileSync(attemptsFile, String(attempts));

const summary = [...missing, ...failed].join("\n\n");
if (attempts >= MAX_ATTEMPTS) {
  // Let Claude stop, and tell the human. The marker stays, so the lock stays on.
  process.stdout.write(JSON.stringify({
    systemMessage: `AC gate: still failing after ${attempts} tries. A human needs to look.\n\n${summary}`,
  }));
  process.exit(0);
}

process.stderr.write(
  `AC gate (try ${attempts} of ${MAX_ATTEMPTS}): you can't finish yet. ` +
    `${failed.length + missing.length} of ${runs.length + missing.length} items fail. Fix the code, not the tests.\n\n${summary}\n`,
);
process.exit(2);

Reads the marker and the Tests, Files and Checks sections of plan.md for both hooks.

.claude/skills/implement/scripts/plan.mjs
// Shared helpers: read plans/.implementing and the tables in plan.md.
import { existsSync, readFileSync } from "node:fs";
import { join } from "node:path";

export const root = process.env.CLAUDE_PROJECT_DIR || process.cwd();
export const markerPath = join(root, "plans", ".implementing");

export function readMarker() {
  if (!existsSync(markerPath)) return null;
  try {
    return JSON.parse(readFileSync(markerPath, "utf8"));
  } catch {
    return null;
  }
}

const strip = (c) => c.trim().replace(/^`([^`]*)`$/, "$1").trim();

/** Rows of the markdown table under "## <heading>", as arrays of cells. */
export function table(md, heading) {
  const lines = md.split("\n");
  const start = lines.findIndex((l) => l.trim().toLowerCase() === `## ${heading}`.toLowerCase());
  if (start < 0) return [];
  const rows = [];
  for (const line of lines.slice(start + 1)) {
    if (line.startsWith("## ")) break;
    if (!line.trim().startsWith("|")) continue;
    const cells = line.trim().replace(/^\||\|$/g, "").split("|").map(strip);
    if (cells.every((c) => /^:?-+:?$/.test(c))) continue;
    rows.push(cells);
  }
  return rows.slice(1); // drop the header row
}

/** Bullet items under "## <heading>", without backticks. */
export function bullets(md, heading) {
  const lines = md.split("\n");
  const start = lines.findIndex((l) => l.trim().toLowerCase() === `## ${heading}`.toLowerCase());
  if (start < 0) return [];
  const out = [];
  for (const line of lines.slice(start + 1)) {
    if (line.startsWith("## ")) break;
    const m = /^\s*-\s+(.*)$/.exec(line);
    if (m) out.push(strip(m[1]));
  }
  return out;
}

export function readPlan(ticket) {
  const p = join(root, "plans", ticket, "plan.md");
  if (!existsSync(p)) return null;
  const md = readFileSync(p, "utf8");
  return {
    md,
    approved: /^Status:\s*approved/im.test(md),
    tests: table(md, "Tests").map(([ac, name, file, command]) => ({ ac, name, file, command })),
    files: table(md, "Files").map(([file, change, what, ac]) => ({ file, change, what, ac })),
    checks: bullets(md, "Checks"),
  };
}

The subagent that writes the tests from the ACs only, and shows they fail for the right reason. It doesn't read the plan's steps or the code that will change.

.claude/agents/test-writer.md
---
name: test-writer
description: Writes the tests for a ticket from its approved acceptance criteria only, before any code exists, and shows that they fail. Used by the implement skill.
tools: Read, Grep, Glob, Write, Edit, Bash
disallowedTools: Agent
---

You write tests from the intent, not from a plan for the code. Another agent writes the code later. If you both worked from the same reading of the plan, the tests and the code would share the same mistake and both would pass.

You get a ticket id. Read only:

- `plans/<TICKET>/acs.md`: the ACs, "must never" rules and out of scope.
- `plans/<TICKET>/sequence.md`: the calls and error paths the user sees.
- The **Tests** table in `plans/<TICKET>/plan.md`: test names, files and commands.
- Existing tests near those files, to follow the team's test style, helpers and fakes.
- The public surface the tests call (endpoints, page routes, public methods), only to know how to call it.

Don't read the Steps or Files sections of `plan.md`, and don't read the code that will change. Test the behavior in the AC, not an implementation.

For each row in the Tests table:

1. Write the test with the exact name and in the exact file from the table.
2. Use the AC's exact values: the same limit, text and status code.
3. "Must never" rows: a property test that makes up many inputs and checks the rule always holds.
4. E2E row: the main flow, as a user does it.
5. Fixed seeds, a fake clock, no shared state between tests.

Then run each test command. Every test must fail, and fail because the behavior is missing, not because of a typo, a missing import or a build error. Fix a test that fails for the wrong reason. A test that passes already tests nothing: fix it.

Return, for each test: the AC, the test name and file, and the last lines of its failing output. Write only test files.

Paths and commands assume a repo with src/Api (.NET), backend/ (PHP) and web/ (Next.js). MCP server names are the names in the repo's .mcp.json. Each team changes them to match its own repo. The files are in examples/ in the repo.
