# Plan: ACs → build plan

Run this in plan mode (`claude --permission-mode plan`), so nothing changes until the human approves. You write one file, after the approval: `plans/<TICKET>/plan.md`. The format is in [references/plan-format.md](references/plan-format.md), and a full example is in [references/example-plan.md](references/example-plan.md).

Ticket: $ARGUMENTS

## 1. Read the intent

Read `plans/<TICKET>/acs.md` and `plans/<TICKET>/sequence.md`.

Stop if:

- either file is missing → "Run /discover <TICKET> first."
- `acs.md` has open questions → list them and stop. No plan without clear ACs.

## 2. Read the code

For every arrow in `sequence.md`, find the code that does it today, or where new code must go. Follow the team's patterns: find a similar feature and plan the same shape. Note every file you will change or create.

## 3. Steps

Numbered steps, small enough to check one by one. Each step ends with the AC it serves: `→ AC1`. A step that serves no AC is a question for the human, not a step.

## 4. Tests first

Tests come from the ACs, not from the code. They are written before any code, and they must fail first.

- One test per AC, with the AC's exact values.
- One property test per "must never" rule.
- One E2E test for the main flow.

Each test gets a row in the Tests table with the **exact command** that runs only that test. `/implement` and its Stop hook run these commands, so they must work as written.

## 5. Files

Every file you will change or create gets a row in the Files table: file, `edit` or `new`, what changes, which AC. Test files too. The drift guard in `/review` compares this table with what really changed.

## 6. Checks

The static check commands for the stacks this plan touches, from the repo's CI. `/implement` runs them before it can finish.

## 7. Risks

What could go wrong, in one line each: a migration, a shared component, a public API change, a feature flag. Each risk names the step it belongs to.

## 8. Ask for approval

This is where the human checks the intent: fixing it here takes minutes, fixing it in a PR takes days. Show all three together, in this order:

1. **The ACs** from `acs.md`: every AC, the "must never" rules and out of scope.
2. **The sequence diagram** from `sequence.md`.
3. **The plan**: steps, tests, files, checks and risks.

Then ask one question:

> Do you approve the ACs, the diagram and this plan? (Yes / No)

In plan mode this is the plan approval prompt.

- **Yes** → write `plans/<TICKET>/plan.md` with `Status: approved (<date>)`, and say: "Start a fresh session and run /implement <TICKET>."
- **No** → ask what is wrong or missing, one question at a time, until it is clear. Change the plan, show all three again, and ask again. If the answer changes an AC or the diagram, stop: run /discover again so `acs.md` and `sequence.md` change first.

Write nothing before the yes.

The exact headings and table columns. Scripts in /implement and /review read them, so the format is fixed.

# plan.md format

`/implement`, its hooks and `/review` read this file with scripts. Keep the headings and table columns exactly as shown.

````markdown
# <TICKET>: <title> — plan

Status: approved (<date>)

## Steps
1. <what> in `<file>` → AC1
2. …

## Tests
| AC | Test | File | Command |
|---|---|---|---|
| AC1 | <TestName> | `<path>` | `<command that runs only this test>` |
| Must never | <PropertyTestName> | `<path>` | `<command>` |
| E2E | <spec name> | `<path>` | `<command>` |

## Files
| File | Change | What | AC |
|---|---|---|---|
| `<path>` | edit | <what changes> | AC1 |
| `<path>` | new | <what> | AC1, AC2 |

## Checks
- `<static check command>`

## Risks
- <risk> (step 3)
````

## Rules

- **Status** is written by `/plan` when the human answers yes to "Do you approve this plan?". The file only exists after that. `/implement` refuses a plan without it.
- **Tests** has one row per AC, one per "must never" rule, and one E2E row. The command runs only that test, in seconds.
- **Files** lists every file that will change or be created, test files included.
- **Checks** are commands that finish in seconds. Slow checks belong in CI.

# JIRA-1234: Phone number on profile — plan

Status: approved (2026-10-28)

## Steps
1. Write the tests in the Tests table. Run them. They must fail. → AC1, AC2, AC3, Must never
2. Add `Phone` (nvarchar(20), optional) to `User` with the `add-ef-migration` skill. → AC1
3. Add the E.164 rule to `ProfileRequestValidator.cs`, using `PhoneNumber.IsE164()` from `Shared/Contact/PhoneNumber.cs`. → AC1
4. In `ProfileService.cs`, save an empty phone as `NULL`. → AC3
5. Add the rate limit policy `profile-save` (2 per second, per user) in `Program.cs` and use it on `PUT /profile`. → AC2
6. Add the phone field and the "Invalid phone number" error to `ProfileForm.tsx`. → AC1, AC3
7. Add the changelog entry. → all

## Tests
| AC | Test | File | Command |
|---|---|---|---|
| AC1 | ProfilePhoneTests.InvalidPhone | `tests/Api.Tests/Profile/ProfilePhoneTests.cs` | `dotnet test tests/Api.Tests --filter "FullyQualifiedName~ProfilePhoneTests.InvalidPhone"` |
| AC2 | ProfilePhoneTests.RateLimit | `tests/Api.Tests/Profile/ProfilePhoneTests.cs` | `dotnet test tests/Api.Tests --filter "FullyQualifiedName~ProfilePhoneTests.RateLimit"` |
| AC3 | ProfilePhoneTests.RemovePhone | `tests/Api.Tests/Profile/ProfilePhoneTests.cs` | `dotnet test tests/Api.Tests --filter "FullyQualifiedName~ProfilePhoneTests.RemovePhone"` |
| Must never | PhoneProperties.AlwaysE164 | `tests/Api.Tests/Profile/PhoneProperties.cs` | `dotnet test tests/Api.Tests --filter "FullyQualifiedName~PhoneProperties"` |
| E2E | profile phone | `web/e2e/profile-phone.spec.ts` | `npx playwright test web/e2e/profile-phone.spec.ts --trace on` |

## Files
| File | Change | What | AC |
|---|---|---|---|
| `src/Domain/Entities/User.cs` | edit | `Phone` property | AC1 |
| `src/Infrastructure/Persistence/Configurations/UserConfiguration.cs` | edit | max length 20 | AC1 |
| `src/Infrastructure/Migrations/*_AddPhoneToUsers.cs` | new | migration (generated) | AC1 |
| `src/Api/Profile/ProfileRequestValidator.cs` | edit | E.164 rule | AC1 |
| `src/Api/Profile/ProfileService.cs` | edit | empty → NULL | AC3 |
| `src/Api/Program.cs` | edit | rate limit policy | AC2 |
| `web/app/profile/ProfileForm.tsx` | edit | phone field, error text | AC1, AC3 |
| `tests/Api.Tests/Profile/ProfilePhoneTests.cs` | new | one test per AC | AC1, AC2, AC3 |
| `tests/Api.Tests/Profile/PhoneProperties.cs` | new | property test | Must never |
| `web/e2e/profile-phone.spec.ts` | new | main flow | AC1 |
| `CHANGELOG.md` | edit | entry | all |

## Checks
- `dotnet build src/Api --no-restore -warnaserror`
- `npx tsc --noEmit -p web`
- `npx eslint web/app/profile`

## Risks
- The migration adds a column to `Users`, a large table. Check the SQL before deploy. (step 2)
- The rate limit partitions by user id. Two tabs share the limit, which is what AC2 says. (step 5)

Paths and commands assume a repo with src/Api (.NET), backend/ (PHP) and web/ (Next.js). MCP server names are the names in the repo's .mcp.json. Each team changes them to match its own repo. The files are in examples/ in the repo.
