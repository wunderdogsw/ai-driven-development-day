# Discover: ticket → precise acceptance criteria

You collect evidence, find what is unclear, ask the user until every acceptance criterion (AC) is precise, and write two files. You never change code. The human decides the intent. You find the questions.

Ticket: $ARGUMENTS

## 1. Fetch the ticket

Read the ticket, its comments and its linked issues from the team's tracker, with the MCP server or CLI in [references/sources.md](references/sources.md). Note the title, description, any ACs already written, and the comments.

If the tracker can't be read, ask the user to paste the ticket. Don't guess what it says.

## 2. Collect evidence

Go through every source in [references/sources.md](references/sources.md), with the MCP server or CLI it names. Use only read tools. Search with the words of the ticket. For each thing you find, keep a reference: file and line, commit hash, PR number or ADR id.

At least: the code and tests of the area, `git log` for those files, and every ADR that uses the ticket's words. A source you can't read goes on the "Not checked" list. Don't skip it silently.

## 3. List gaps and conflicts

Before you ask anything, show the list:

```
Gaps (the ticket doesn't say):
- G1 Which phone number formats are accepted?
- G2 What happens on a fast double-click on Save?

Conflicts (two sources disagree):
- C1 The ticket says "phone number". ADR-012 says contact data is stored in E.164.

Not checked:
- Figma (server not connected)
```

If there are more than 8 gaps, the ticket is too big. Suggest how to split it and stop.

## 4. Ask until precise

One question at a time. Each question:

- quotes the evidence that made it a question;
- gives 2–4 concrete options;
- marks one option as recommended only when the evidence supports it.

Save every answer as a decision with who decided it (name or role): `Decision: any E.164 (Product Owner)`. An answer can open a new question. Ask it.

## 5. Write the ACs

Rules and format: [references/ac-format.md](references/ac-format.md). A full worked example: [references/examples.md](references/examples.md).

Check every AC against the five rules before you write it. If one fails, it is a new question for step 4.

## 6. Draw the sequence diagram

Mermaid, as detailed as possible: every actor, call, database write and error path. Label every arrow that serves an AC. A missing arrow is a gap: go back to step 4.

## 7. Write the files

- `plans/<TICKET>/acs.md`
- `plans/<TICKET>/sequence.md`

Write nothing else.

## 8. Hand over

```
plans/JIRA-1234/acs.md — 3 ACs, 1 must-never rule, 0 open questions
plans/JIRA-1234/sequence.md — 4 actors, 3 error paths
Not checked: Figma (server not connected)

Review both files. When they are right, start a fresh session and run /plan JIRA-1234.
```

## Done when

- every AC passes the five rules;
- every AC has evidence or a decision;
- open questions are empty, or the user said to keep them open.

Where the evidence lives, the MCP tool or CLI command for each source, and why that one. This is the file each team changes to match its own servers and tools.

# Sources

Where the evidence for a ticket lives, and how to read it. Every tool here only reads. Keep the rows for the tools your team uses and delete the rest.

The rule from Part 2: use a CLI when there is a good one (it costs fewer tokens). Use an MCP server for systems with no good CLI, and for tools you use often. MCP server names (`atlassian`, `linear`, `ado`, `azure`, `figma`, `notion`) are the names in the repo's `.mcp.json`.

## Tickets: pick your tracker

Use the row for the team's tracker. Change `allowed-tools` in `SKILL.md` to match: pre-approve only the read tools.

| Tracker | Read the ticket, comments and links | Search related tickets | Pre-approve |
|---|---|---|---|
| Jira | Atlassian Rovo MCP: `getAccessibleAtlassianResources` once (for the `cloudId`), then `getJiraIssue`, `listJiraIssueComments`. Fallback: `acli jira workitem view <id> --fields '*all' --json` | `searchJiraIssuesUsingJql` | `mcp__atlassian__getJiraIssue` and the other read tools |
| Linear | Linear MCP, read-only endpoint `https://mcp.linear.app/mcp/readonly`. Tool names: check `/mcp` | the server's issue search | `mcp__linear` (the whole server is safe on the read-only endpoint) |
| GitHub Issues | `gh issue view <n> --comments --json title,body,comments,labels`. Sub-issues and links: `gh api repos/{owner}/{repo}/issues/<n>/sub_issues` | `gh issue list --search "<words>" --state all` | `Bash(gh issue view *) Bash(gh issue list *)` |
| Azure Boards | Azure DevOps MCP: `wit_work_item` (`get`, `list_comments`). Fallback: `az boards work-item show --id <id>` | `search_workitem` | `mcp__ado__wit_work_item mcp__ado__search_workitem` |
| GitLab issues | `glab issue view <n> --comments` | `glab issue list --search "<words>"` | `Bash(glab issue view *) Bash(glab issue list *)` |

GitHub and GitLab have good CLIs, so use them. Jira, Linear and Azure Boards have more in the MCP server (comments, links, structured fields).

## PRs and review comments

| Host | Read merged PRs and their review threads |
|---|---|
| GitHub | `gh pr list --state merged --search "<words>"`, `gh pr view <n> --comments`, review comments with `gh api repos/{owner}/{repo}/pulls/<n>/comments` |
| Azure DevOps | Azure DevOps MCP: `repo_pull_request` (`list`, `get`), `repo_pull_request_thread` (`list`, `list_comments`) |
| GitLab | `glab mr list --merged --search "<words>"`, `glab mr view <n> --comments` |

## Decisions and docs

| Where | Read with |
|---|---|
| ADRs in the repo | `Read` and `Grep` in `docs/adr/` |
| Confluence | Atlassian Rovo MCP: `searchConfluence` (CQL), `getConfluenceContent` |
| Notion | Notion MCP: search and fetch pages |
| Azure DevOps wiki | Azure DevOps MCP, wiki tools |
| Linear documents | Linear MCP |

## The rest

| Source | What it tells | How to read it | Why this way |
|---|---|---|---|
| Code and tests | How it works today | `Grep` and `Read` in `src/Api/`, `backend/`, `web/` and their test folders | Built-in tools, no server needed |
| Commit history | What changed, when, and why | `git log --oneline -n 30 -- <files>`, `git log -S "<word>" --oneline` | git is the best tool for this |
| Logs | Real errors in the area | Azure MCP: the monitor log query tool, KQL on the Log Analytics workspace, last 14 days | Real errors show missing error cases |
| Designs | What the user sees | Figma MCP: the frame linked in the ticket | Exact texts and states, not a guess from a screenshot |
| Architecture | System boundaries | `docs/architecture/*.dsl` (C4) | Files in the repo |
| CI | What runs on every change | `azure-pipelines.yml`, `.github/workflows/`, `.gitlab-ci.yml` | Files in the repo |

## Set up once, for the whole team

- Add the servers to the repo's `.mcp.json` so every teammate gets the same ones. Use the official servers (Atlassian Rovo, Linear, Azure DevOps, Azure, Figma, Notion), and their read-only endpoint or mode where they have one.
- Turn on read-only mode where the server has one. For Azure DevOps, send the `X-MCP-Readonly: true` header.
- This skill pre-approves only read tools. A write tool, if it is ever called, still asks the user.
- The Azure MCP log query tool is not pre-approved, because its name differs between server versions. Check the name in `/mcp`, then add it to `allowed-tools`.

## Order

1. Ticket, comments and linked issues.
2. Code and tests: what exists today.
3. ADRs, wiki and architecture: what was decided.
4. Commit history and past PRs: why it is the way it is, and what broke before.
5. Logs and designs: what happens in production, and what the user sees.

## When a source can't be read

The server is not connected, sign-in failed, or there is no access. Put it on the "Not checked" list with the reason. Don't skip it silently and don't read it some other way.

## What counts as evidence

A reference someone else can open: `src/Api/Profile/ProfileRequestValidator.cs:42`, `a1b2c3d`, `PR #482`, `ADR-012`, a ticket id (`PROF-881`, `ENG-142`, `#311`), a Figma frame link, a KQL query and its result count. "It seems that" is not evidence.

The five precision rules, “must never” rules and the templates for acs.md and sequence.md.

# Acceptance criteria

## The five rules

1. **One behavior per AC.** "And" between two results means two ACs.
2. **Concrete values, not adjectives.** "2 saves within 1 second", not "fast". "Max 20 characters", not "short".
3. **Error cases and permissions included.** What happens when it fails, and who may do it.
4. **Out of scope written down.** What the ticket does not cover.
5. **Two people would agree on pass or fail.** If you can't write the test, the AC isn't done.

## Format

Given / when / then, with exact values and exact texts:

> Given a logged-in user, when they save a phone number that isn't in E.164 format, then the save is blocked and the field shows "Invalid phone number".

## "Must never" rules

Examples say what should happen. Rules say what must never happen. Each rule becomes a property test: a test that makes up thousands of inputs and tries to break the rule.

| Kind | Example |
|---|---|
| Always equal | The cart total always equals the sum of its lines. |
| Never below | A balance never goes negative. |
| Twice = once | Saving twice gives the same result as saving once. |

Look for one in every ticket that saves, counts or converts something.

## acs.md template

```markdown
# <TICKET>: <title>

## AC1 <short name>
Given …, when …, then ….
Evidence: <reference> · Decision: <answer> (<name>)

## Must never
- <rule>

## Out of scope
- <item>

## Open questions
- (none)

## Not checked
- <source and why>
```

## sequence.md template

````markdown
# <TICKET>: sequence

```mermaid
sequenceDiagram
  actor User
  participant Web as Web (Next.js)
  participant API as API (.NET)
  participant DB as Azure SQL
  User->>Web: <action>
  Web->>API: <call>
  alt <error case> (AC1)
    API-->>Web: <status>
  else <happy path>
    API->>DB: <write>
    API-->>Web: 200 OK
  end
```
````

# Worked example: JIRA-1234

## The ticket

> **JIRA-1234 Phone number on profile**
> Users should be able to add their phone number to their profile.

## Evidence found

- `src/Api/Profile/ProfileController.cs:31` — `PUT /profile` saves the whole profile.
- `src/Api/Profile/ProfileRequestValidator.cs` — FluentValidation, no phone rule.
- `web/app/profile/ProfileForm.tsx` — the form, no phone field.
- `PR #482` (Azure DevOps MCP) — fixed duplicate writes on a fast double-click on Save in the address form. A review thread says: "we should rate-limit all profile saves".
- `ADR-012` (Confluence, Atlassian MCP) — "All contact data is stored in E.164."
- Logs (Azure MCP, last 14 days) — 37 `DbUpdateException` on `PUT /profile`, all within 1 second of another save by the same user.
- Figma frame "Profile / Edit" (Figma MCP) — error text under the field: "Invalid phone number".

## Gaps and conflicts shown to the user

```
Gaps:
- G1 Which phone numbers must be accepted?
- G2 What happens on a fast double-click on Save?
- G3 Can a user remove their phone number?

Conflicts:
- C1 The ticket says "phone number". ADR-012 says contact data is E.164.

Not checked:
- (none)
```

## Questions and answers

> The ticket says "phone number". ADR-012 says we store all contact data in E.164. Which numbers must be accepted?
> a) Finnish only  b) Any E.164 (recommended: matches ADR-012)  c) Anything with digits

Answer: b. → `Decision: any E.164 (Product Owner)`

> PR #482 fixed duplicate writes on a fast double-click in the address form, and the logs show 37 errors from saves less than 1 second apart. What should happen here?
> a) Ignore it  b) Limit to 2 saves per second, the third gets 429  c) Disable the button while saving

Answer: b. → `Decision: 2 per second (Product Owner)`

> Can a user remove their phone number after saving it?
> a) Yes, an empty field removes it  b) No

Answer: a. → `Decision: empty removes it (Product Owner)`

## Bad → good

| Bad | Why it fails | Good |
|---|---|---|
| "Phone number is validated." | No value, no result. | "…when they save a phone number that isn't E.164, then the save is blocked and the field shows 'Invalid phone number'." |
| "Saving is fast and safe." | Two behaviors, two adjectives. | "…when they save more than 2 times within 1 second, then the third save gets HTTP 429." |
| "Works like the address field." | Points to other code, not to a behavior. | Write the behavior out. |

## plans/JIRA-1234/acs.md

```markdown
# JIRA-1234: Phone number on profile

## AC1 Phone must be E.164
Given a logged-in user, when they save a phone number that isn't E.164,
then the save is blocked and the field shows "Invalid phone number".
Evidence: ADR-012, Figma "Profile / Edit" · Decision: any E.164 (Product Owner)

## AC2 Save rate limit
Given a logged-in user, when they save their profile more than 2 times within 1 second,
then the third save gets HTTP 429.
Evidence: PR #482, logs (37 errors in 14 days) · Decision: 2 per second (Product Owner)

## AC3 Remove the phone number
Given a logged-in user with a saved phone number, when they save the profile with an empty phone field,
then the phone number is removed and the profile shows no phone number.
Decision: empty removes it (Product Owner)

## Must never
- A saved phone number is never stored in another format than E.164.

## Out of scope
- SMS verification.
- Phone numbers for company accounts.

## Open questions
- (none)

## Not checked
- (none)
```

## plans/JIRA-1234/sequence.md

```mermaid
sequenceDiagram
  actor User
  participant Web as Web (Next.js)
  participant API as API (.NET)
  participant DB as Azure SQL
  User->>Web: Save profile
  Web->>API: PUT /profile
  alt phone not E.164 (AC1)
    API-->>Web: 400 not E.164
    Web-->>User: "Invalid phone number"
  else third save within 1 s (AC2)
    API-->>Web: 429
  else empty phone (AC3)
    API->>DB: UPDATE Users SET Phone = NULL
    API-->>Web: 200 OK
  else valid
    API->>DB: UPDATE Users SET Phone
    API-->>Web: 200 OK
  end
```

Paths and commands assume a repo with src/Api (.NET), backend/ (PHP) and web/ (Next.js). MCP server names are the names in the repo's .mcp.json. Each team changes them to match its own repo. The files are in examples/ in the repo.
