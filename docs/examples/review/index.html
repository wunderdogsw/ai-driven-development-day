/review

The review skill leads a team of independent subagents: two verify facts, two or three review the code and the logic. It cross-checks what they found, keeps what holds up, and writes review comments, on the PR or in a local file before there is a PR. It never edits code.

What makes it good

  • Machines firstStatic checks, file drift, docs and the grade run as commands, with the same result every time. Subagents only do what needs reading.
  • Flaky tests and a traceEach AC test runs 3 times; a test that passes only sometimes is blocking. The E2E test runs with a Playwright trace that goes in the PR evidence.
  • Other reviewers count tooCodeRabbit, Greptile and SonarCloud comments on the PR join the cross-check as one more independent source.
  • Independent subagentsEach subagent gets only the packet and its own task, never another one's findings. When two of them find the same thing alone, it means something.
  • Verify and review are separateVerifiers run tests and the app and report facts. Reviewers read code (review-code) and logic against the ACs (review-logic).
  • The diagram is drawn twiceThe flow verifier redraws the sequence diagram from the code without looking at the plan, then compares arrow by arrow. A new arrow on a file the drift guard also flagged counts as found twice.
  • A third reviewer when it mattersreview-fresh-eyes reads without the plan, for Large or Critical changes or when the other two disagree.
  • Cross-check rulesFound twice = confirmed. Found once = the lead checks it. Facts beat readings. Disagreement goes to the human. Rejected findings are listed with a reason.
  • Comments people can act onConventional Comments labels, one problem per comment, why and evidence, a fix when there is one. Examples for PR comments and for a local review before the PR.
  • Asks before it postsComments are written to a file first. Posting to the PR is a write, so the user approves it.

# Review a change

You lead the review. Machines run the mechanical checks. Independent subagents verify and review. You cross-check what they found, and write the comments. You never edit code, tests or plans. The only files you write are in `plans/<TICKET>/review/`.

Ticket: $ARGUMENTS. If empty, take it from the branch name (`feature/JIRA-1234-…`). If there is none, find the open PR for the branch (GitHub: `gh pr view`; Azure DevOps: MCP `repo_pull_request`; GitLab: `glab mr view`) and use its linked ticket. If there is still none, ask.

## 1. Prepare the packet

Collect the inputs and write them to `plans/<TICKET>/review/packet.md`. Every subagent gets this file and nothing else from you.

- Base: `origin/main`.
- Changed files: `git diff --name-only origin/main` plus `git ls-files --others --exclude-standard`.
- How to see the diff: `git diff origin/main -- <file>`.
- Intent: `plans/<TICKET>/acs.md`, `sequence.md`, `plan.md`. No plan files? Read the ticket from the team's tracker (the same way as the `discover` skill's `sources.md`: Jira, Linear, GitHub, Azure Boards or GitLab), put its text in the packet, and write "No plan" at the top.
- The check commands from [references/checks.md](references/checks.md) for the stacks the change touches.
- The findings format: [references/findings.md](references/findings.md).
- **Other reviewers already on the PR.** If a PR exists, collect the comments that CodeRabbit, Greptile or the SonarCloud quality gate left on it. They go into the cross-check as one more independent source (`P`). Don't send them to the subagents.

Pre-grade the change: `node ${CLAUDE_SKILL_DIR}/scripts/grade.mjs --base origin/main` ([references/grading.md](references/grading.md)). It decides how many reviewers run in step 4.

## 2. Mechanical checks (you, no model judgement)

Run these yourself. They give the same result every time.

- Static checks from `checks.md`. Keep only what failed, at most 20 lines per command.
- File drift: `node ${CLAUDE_SKILL_DIR}/scripts/drift-guard.mjs --plan plans/<TICKET>/plan.md --base origin/main`
- Docs: changelog for new behavior, ADR for a changed decision, README for changed setup.

## 3. Verification subagents (parallel, independent)

Start both in **one message**, so they run at the same time. Give each one the packet path and its task. Nothing else.

| Subagent | Checks |
|---|---|
| `review-ac-verifier` | One test per AC exists, runs and passes, and tests the AC's values. Runs each AC test 3 times to catch flaky tests, and checks for fixed seeds and frozen clocks. Property test per "must never" rule. E2E for the main flow, with a Playwright trace (and video if the config records it). Test files changed after the plan was approved. |
| `review-flow-verifier` | Redraws the sequence diagram from the changed code without looking at the plan's one, then compares the two arrow by arrow: match, missing, new, changed. Saves both to `review/sequence-from-code.md`. If the web app runs locally, goes through the main flow with the Playwright MCP server and saves a screenshot per AC. |

Skip `review-ac-verifier` and the diagram part when there is no plan. Say so in the output.

## 4. Reviewer subagents (parallel, independent)

Start them in **one message**, together with step 3 if you can. Each one reviews alone. **Never pass one reviewer's findings to another.** Independent reviews are what make agreement mean something.

| Subagent | Looks at | Runs |
|---|---|---|
| `review-code` | Code level: bugs, error handling, nulls, security, performance, dead code, duplication, team conventions | always |
| `review-logic` | Business logic against the ACs: missing, extra, edge cases, concurrency, "must never" rules, data consistency | always |
| `review-fresh-eyes` | The diff and the ticket title only, no ACs or plan. Anything that looks wrong to someone who wasn't in the planning | pre-grade Large or Critical, or when `review-code` and `review-logic` disagree |

## 5. Cross-check the findings

Put every finding from steps 2–4 in one list. Then:

1. **Group.** Same file, lines within 10 of each other, same problem → one finding. Keep every source: "found by review-code, review-logic".
2. **Agreement.** Found by two or more independent sources (subagents, mechanical checks, or another reviewer tool on the PR) → **confirmed**.
3. **Single finding.** Found by one → check it yourself: read the lines, run the test or the check if one exists. Then **confirmed**, **rejected** (with the reason), or **unsure**.
4. **Facts beat readings.** A test run or a check output outranks a reviewer's reading. If a reviewer says AC2 is not handled but the AC2 test passes, check that the test really uses the AC2 values before you reject the finding.
5. **Disagreement.** Two subagents say opposite things → **unsure**, both views go to the human.
6. **Diagram and drift.** A `new` or `changed` arrow and a drift-guard "not in the plan" line on the same file are the same finding, found twice → confirmed. A `missing` arrow and a missing AC test from `review-ac-verifier` for the same AC → confirmed.
7. **Severity.** `blocking` only when it breaks an AC, a "must never" rule, security, data, or a check. Everything else is `non-blocking` or `nitpick`.
8. **Nothing is dropped silently.** Rejected findings are listed with their reason in `review.md`.

Unsure findings become `question:` comments. Confirmed findings become comments with their label.

## 6. Grade

Start from the script's grade. Raise it if the review found business logic, a data change or a security finding that the paths didn't show. Never lower it. See [references/grading.md](references/grading.md).

## 7. Write the comments

How to write them, with examples: [references/comments.md](references/comments.md).

**Is there a PR?** GitHub: `gh pr view --json number,url`. Azure DevOps: MCP `repo_pull_request` (`list`, source branch = current branch). GitLab: `glab mr view`.

- **Not yet a PR** → write `plans/<TICKET>/review/review.md`: the summary, the fix list (blocking first), the comments by file with `path:line`, and the rejected findings. Tell the user: "Fix the blocking items in review.md, then run /review again."
- **PR exists** → write the comments to `plans/<TICKET>/review/comments.md` first and show them. Ask: "Post N comments to PR #<n>?" Only on yes, post each on its file and line, plus one summary comment. GitHub: one review with `gh api repos/{owner}/{repo}/pulls/<n>/reviews` (inline comments in `comments`). Azure DevOps: MCP `repo_pull_request_thread_write` (`create`). GitLab: `glab api` merge request discussions with a position. This write is not pre-approved, so the user approves it.

# Findings format

Every subagent returns its findings in this format, and nothing else. No summary, no praise.

```
- id: L2
  where: src/Api/Profile/ProfileService.cs:57
  kind: bug | security | performance | maintainability | logic | missing | extra | test | docs
  severity: blocking | non-blocking | nitpick
  claim: One sentence on what is wrong.
  evidence: The code lines, or the command and its output, that show it.
  ac: AC3            # if it is about an AC, else leave out
  confidence: high | medium | low
```

Rules:

- `where` is one file and one line (or a range like `57-63`). A finding without a place is not a finding.
- `evidence` is something the lead can check: quoted code, a test name and its result, a command and its output. "Looks wrong" is not evidence.
- One problem per finding. Two problems on the same line are two findings.
- `blocking` only when it breaks an AC, a "must never" rule, security, data, or a check.
- If you found nothing in your area, return `findings: []` and one line on what you checked.

The id prefix shows the source: `V` ac-verifier, `F` flow-verifier, `C` review-code, `L` review-logic, `E` review-fresh-eyes, `M` mechanical checks, `P` other reviewers already on the PR (CodeRabbit, Greptile, SonarCloud).

# Writing review comments

## Rules

1. **One problem per comment**, on the line where it is.
2. **Label first**, from [Conventional Comments](https://conventionalcomments.org): `issue (blocking):`, `issue (non-blocking):`, `suggestion (non-blocking):`, `question:`, `nitpick:`. The reader knows at once if it must be fixed.
3. **What, then why.** One sentence on what is wrong. One or two on why it matters: the AC, the rule, or what breaks.
4. **Evidence.** The line, the test, the command output. The reader can check it in seconds.
5. **A fix when you have one**, as a code block. Keep it small.
6. **About the code, not the person.** "This line saves…", not "You save…".
7. **Plain words. No praise padding, no "just", no "obviously".**
8. **Unsure? Ask.** A `question:` comment says what you checked and what you don't know.

## PR comments

These go on the file and line in the PR. Azure DevOps and GitHub render the markdown. On GitHub, a ` ```suggestion ` block lets the author apply the fix with one click.

### Blocking issue

````markdown
**issue (blocking):** An empty phone number is saved as `""`, not removed.

AC3 says an empty field removes the phone number. This line stores `request.Phone ?? ""`, so the user still has a phone value, and `""` breaks the "always E.164" rule.

```csharp
user.Phone = string.IsNullOrWhiteSpace(request.Phone) ? null : request.Phone;
```

Found by review-logic and ac-verifier (no AC3 test).
````

### Missing test

```markdown
**issue (blocking):** AC3 has no test.

`plan.md` lists `ProfilePhoneTests.RemovePhone` for AC3. It is not in `ProfilePhoneTests.cs`. Add it before the fix above, so the test fails first.
```

### Flaky test

```markdown
**issue (blocking):** `ProfilePhoneTests.RateLimit` is flaky: it passed 2 of 3 runs.

It sends three saves and expects the third to get 429 within 1 second, using the real clock. On a slow run the window passes before the third save. Use the fake `TimeProvider` the other rate limit tests use (`tests/Api.Tests/Support/FakeTime.cs`), so the test controls the time.
```

### Non-blocking suggestion

````markdown
**suggestion (non-blocking):** Use the existing E.164 helper.

`PhoneNumber.IsE164()` in `Shared/Contact/PhoneNumber.cs:12` already does this check, with tests. A second regex here can drift from it.

```csharp
RuleFor(x => x.Phone).Must(PhoneNumber.IsE164).When(x => x.Phone is not null);
```
````

### Question

```markdown
**question:** Should the rate limit be per user or per session?

AC2 says "a logged-in user". The policy here partitions by session id (`Program.cs:88`), so one user with two tabs gets 4 saves per second. review-code and review-logic read this differently, so a human should decide.
```

### Diagram drift

```markdown
**question:** This adds a cache write that the plan doesn't have.

The sequence diagram in the plan ends with `API → DB: UPDATE Users`. The diagram redrawn from the code also has `API → Cache: SET profile` here, and `ProfileService.cs` is changed but not in the plan's file table. Was the cache part of the design? If yes, add it to `sequence.md` and `plan.md`. If not, remove it from this change.

Found by flow-verifier and drift-guard.
```

### Nitpick

```markdown
**nitpick:** `phoneNr` → `phoneNumber`, like the rest of the file.
```

### Summary comment (one per PR)

```markdown
## Review: JIRA-1234 · grade Large · needs a human

**Evidence**
- AC1 → `ProfilePhoneTests.InvalidPhone` → passed
- AC2 → `ProfilePhoneTests.RateLimit` → passed
- AC3 → no test → **missing**
- Must never → `PhoneProperties` (1,000 inputs) → passed
- E2E → `web/e2e/profile.spec.ts` → passed 3 of 3 runs, trace attached (`e2e-trace.zip`)
- Flaky tests: none
- Screenshots: AC1, AC2 (AC3 not shown: not built)
- SonarCloud quality gate: passed

**Checks:** eslint failed on `ProfileForm.tsx:48`. Drift: `Shared/StringUtils.cs` changed, not in the plan.

**Diagram** (redrawn from the code, compared with `sequence.md`)

| Arrow | Result |
|---|---|
| API → DB: UPDATE Users SET Phone = NULL (AC3) | missing |
| API → Cache: SET profile | new, not in the plan |
| API → Web: 200 OK | changed: now returns the profile body |
| 4 other arrows | match |

**Blocking (2):** AC3 saves `""` instead of removing the phone. AC3 has no test.
**Questions (1):** rate limit per user or per session.

Reviewed by 5 independent subagents and cross-checked with CodeRabbit's comments. Each blocking item was found by at least two sources, or checked by running the code.
```

## Bad → good

| Bad | Why it fails | Good |
|---|---|---|
| "This is wrong." | No what, no why, no fix. | `issue (blocking):` + what + AC + fix |
| "Why did you do it like this??" | About the person, sounds like blame, no question to answer. | `question:` + what you checked + the exact thing you don't know |
| "Maybe consider possibly refactoring this a bit?" | No label, no reason, can't be acted on. | `suggestion (non-blocking):` + the helper that exists + the code |
| "LGTM 👍" on a change with no AC3 test | Approves without evidence. | The summary comment with the evidence list |
| 12 nitpicks and 1 blocker mixed together | The blocker gets lost. | Blocking first, nitpicks last or left out |

# Checks

Run only the stacks the change touches. Each command must finish in seconds. If one is slow, run it on the changed project or files only.

## .NET (`src/`, `tests/`)

| Check | Command |
|---|---|
| Build with analyzers | `dotnet build src/Api --no-restore -warnaserror` |
| One test | `dotnet test tests/Api.Tests --filter "FullyQualifiedName~<TestName>"` |
| Property tests | `dotnet test tests/Api.Tests --filter Category=Properties` |

## PHP (`backend/`)

| Check | Command |
|---|---|
| Static analysis | `vendor/bin/phpstan analyse --no-progress --error-format=raw <changed files>` |
| One test | `vendor/bin/phpunit --filter <TestName>` |

## Next.js (`web/`)

| Check | Command |
|---|---|
| Types | `npx tsc --noEmit -p web` |
| Lint | `npx eslint <changed files>` |
| Dead code, duplication | `npx fallow` (in `web/`) |
| E2E main flow | `npx playwright test <spec file>` |

## Quality gate

If the repo uses SonarCloud, read the quality gate result for the branch or PR (coverage on new code, duplication, complexity, security hotspots) from the SonarCloud project page or its API. A failed gate is a mechanical finding (`M`). It covers .NET, PHP and TypeScript with one gate.

## By reading

For .NET and PHP there is no Fallow. Read the changed code for:

- a new method or class nothing calls;
- a block of 6+ lines that is the same as code that already exists (search for it);
- a method longer than 40 lines, or nested more than 3 levels;
- a new helper that does what an existing helper already does (search `Shared/`, `backend/src/Support/`).

Small, Medium, Large, Critical, with the paths that set each grade. The pre-grade decides if the third reviewer runs.

# PR grade

`scripts/grade.mjs` sets the grade from the file list, with the rules in `grading.json`. The same files always get the same grade. Change the paths in `grading.json` to match your repo.

| Grade | When | What happens |
|---|---|---|
| **Critical** | Any file matches `critical` (migrations, persistence, database, auth, payments, core domain) | Human gate, mandatory |
| **Large** | More than 15 files, or more than one project, or a file matches `businessLogic` | Needs a human |
| **Medium** | More than 5 files, no business logic | Machine review is enough |
| **Small** | 5 files or fewer, no business logic | Auto-merge when all checks pass |

The script grades only the file list. In step 6 of the review, raise the grade if the review found business logic, a data change or a security finding that the paths didn't show. Never lower it.

Always one line with the reason: the rule and the file that set the grade.

Test folders are not in `projects`, so a change to `src/` with its tests is still one project.

Compares the Files table in plan.md with the changed and new files, globs included. --markdown gives a PR comment. Tested.

.claude/skills/review/scripts/drift-guard.mjs
#!/usr/bin/env node
// Compares the Files table in plan.md with the files the change touched.
// Usage: node drift-guard.mjs --plan plans/JIRA-1234/plan.md [--base origin/main] [--markdown]
// Exit code 1 when a planned file is missing.
import { execFileSync } from "node:child_process";
import { existsSync, readFileSync } from "node:fs";
import { matches } from "./glob.mjs";

const arg = (name, fallback) => {
  const i = process.argv.indexOf(name);
  return i > -1 && process.argv[i + 1] && !process.argv[i + 1].startsWith("--") ? process.argv[i + 1] : fallback;
};
const planPath = arg("--plan");
const base = arg("--base", "origin/main");
const markdown = process.argv.includes("--markdown"); // for a PR comment
if (!planPath || !existsSync(planPath)) {
  console.error("Usage: drift-guard.mjs --plan plans/<TICKET>/plan.md [--base origin/main] [--markdown]");
  process.exit(2);
}

// Only the table under "## Files": | File | Change | What | AC |
const lines = readFileSync(planPath, "utf8").split("\n");
const start = lines.findIndex((l) => l.trim().toLowerCase() === "## files");
const planned = [];
for (const line of start < 0 ? [] : lines.slice(start + 1)) {
  if (line.startsWith("## ")) break;
  if (!line.trim().startsWith("|")) continue;
  const cells = line.trim().replace(/^\||\|$/g, "").split("|").map((c) => c.trim().replace(/^`([^`]*)`$/, "$1"));
  const [file, change = "", what = "", ac = ""] = cells;
  if (!file || /^:?-+:?$/.test(file) || file.toLowerCase() === "file") continue;
  planned.push({ file, change: change.toLowerCase(), what, ac });
}

const git = (...a) => execFileSync("git", a, { encoding: "utf8" }).split("\n").filter(Boolean);
const changed = [...new Set([...git("diff", "--name-only", base), ...git("ls-files", "--others", "--exclude-standard")])];
const hit = (p, c) => (p.file.includes("*") ? matches(c, p.file) : c === p.file || c.endsWith("/" + p.file));

const done = planned.filter((p) => changed.some((c) => hit(p, c)));
const missing = planned.filter((p) => !changed.some((c) => hit(p, c)));
const unplanned = changed.filter((c) => !planned.some((p) => hit(p, c)) && !c.startsWith("plans/"));

const out = [`✓ ${done.length} of ${planned.length} planned files changed`];
for (const c of unplanned) out.push(`! ${c} changed, not in the plan`);
for (const p of missing) out.push(`✗ ${p.file} missing (${p.change}, ${p.what}${p.ac ? `, ${p.ac}` : ""})`);

console.log(markdown ? `### File drift\n\nPlan: \`${planPath}\`\n\n${out.map((l) => `- ${l}`).join("\n")}` : out.join("\n"));
process.exit(missing.length ? 1 : 0);

.claude/skills/review/scripts/grade.mjs
#!/usr/bin/env node
// Grades a change from its file list with the rules in references/grading.json.
// Usage: node grade.mjs [--base origin/main] [--json]
// Prints the grade and the rule that set it. Same input, same grade, every time.
import { execFileSync } from "node:child_process";
import { readFileSync } from "node:fs";
import { dirname, join } from "node:path";
import { fileURLToPath } from "node:url";
import { matches } from "./glob.mjs";

const here = dirname(fileURLToPath(import.meta.url));
const rules = JSON.parse(readFileSync(join(here, "..", "references", "grading.json"), "utf8"));
const i = process.argv.indexOf("--base");
const base = i > -1 ? process.argv[i + 1] : "origin/main";

const git = (...a) => execFileSync("git", a, { encoding: "utf8" }).split("\n").filter(Boolean);
const files = [...new Set([...git("diff", "--name-only", base), ...git("ls-files", "--others", "--exclude-standard")])]
  .filter((f) => !f.startsWith("plans/"));

const hits = (globs) => files.filter((f) => globs.some((g) => matches(f, g)));
const projects = new Set(files.map((f) => Object.keys(rules.projects).find((p) => matches(f, rules.projects[p]))).filter(Boolean));

let grade, reason;
const critical = hits(rules.critical);
const logic = hits(rules.businessLogic);
if (critical.length) [grade, reason] = ["Critical", `touches ${critical[0]}`];
else if (files.length > rules.mediumMaxFiles) [grade, reason] = ["Large", `${files.length} files (more than ${rules.mediumMaxFiles})`];
else if (projects.size > 1) [grade, reason] = ["Large", `${projects.size} projects: ${[...projects].join(", ")}`];
else if (logic.length) [grade, reason] = ["Large", `business logic in ${logic[0]}`];
else if (files.length > rules.smallMaxFiles) [grade, reason] = ["Medium", `${files.length} files, no business logic`];
else [grade, reason] = ["Small", `${files.length} files, no business logic`];

const action = rules.actions[grade];

// Tiny glob matcher: ** = any folders, * = anything but "/".
export function globToRegExp(glob) {
  let re = "";
  for (let i = 0; i < glob.length; i++) {
    const c = glob[i];
    if (c === "*" && glob[i + 1] === "*") {
      re += glob[i + 2] === "/" ? "(?:.*/)?" : ".*";
      i += glob[i + 2] === "/" ? 2 : 1;
    } else if (c === "*") re += "[^/]*";
    else re += c.replace(/[.+?^${}()|[\]\\]/g, "\\$&");
  }
  return new RegExp(`^${re}$`);
}
export const matches = (file, glob) => globToRegExp(glob).test(file);
